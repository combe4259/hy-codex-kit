# playbook: wrapup

제출 전(종료 15~20분 전)에 사용한다. 새 기능을 추가하지 않는다.

## 점검
0. 사용자가 `/review`를 아직 안 돌렸다면 먼저 권한다.
1. 깨끗한 상태에서 README의 "빠른 시작"과 "테스트"를 그대로 따라 실행해 본다. 처음 보는 사람이 README만으로 실행할 수 있어야 한다.
2. 테스트와 헬스체크 결과를 `docs/VERIFICATION.md`에 반영한다.
3. 과제 안내의 필수 파일·파일명·경로가 모두 있는지 확인한다.
4. 비밀값 하드코딩, 불필요한 대용량 파일이 없는지 확인한다.
5. `git status`로 커밋 안 된 변경이 없는지 확인하고, 있으면 커밋한다.
6. `docs/PLAN.md`의 성공 기준마다 충족 / 부분 충족 / 미충족을 표시한다. 위험 시나리오마다 구현했는지, 한계로 남겼는지 표시한다.
7. `docs/VERIFICATION.md`의 "남은 한계"와 "깨지는 조건"을 솔직하게 채운다.

## 내가 만든 것 요약 (후속 질문 대비)
사용자에게 아래를 각각 2~3줄로 설명한다. 항상 `파일:라인`을 함께 적는다.
- 문제를 어떻게 정의했고, 실무자 요구 중 무엇을 우선했나. 명시되지 않은 것 중 무엇을 직접 정했나
- 전체 구조와 데이터 흐름
- 가장 중요한 설계 결정 2~3개: 왜 / 대안 / 이 범위에서 충분한 이유
- 각 결정에 대해 예상 질문과 핵심 답:
  - 규모가 커지면(서버 여러 대, 데이터 10배) 여전히 동작하나?
  - 같은 요청이 동시에·중복으로 오면?
  - 테스트에선 통과했는데 실제 환경에서 깨진다면 원인은?
  - 순서나 구조를 바꾸면 무엇이 달라지나?
- 무엇을 어떻게 검증했나 (반복 횟수 포함)
- 남은 한계와 시간이 더 있으면 할 일
- AI 제안 중 그대로 따르지 않고 바꾼 것이 있다면 무엇이고 왜인가
