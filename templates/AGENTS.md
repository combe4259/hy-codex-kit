# AGENTS.md

## 프로젝트
- 문제: (실무자 요청 한 줄 요약)
- 결과물: (무엇을 만들어 제출하는가)
- 세부 내용은 `docs/PLAN.md`가 기준이다.

## 명령어
- 실행: (예: `docker compose up --build -d`)
- 테스트: (예: `python3 -m pytest -q`)
- 헬스체크: (예: `curl -s localhost:3000/health`)

## 작업 순서
1. 구현 전에 `docs/PLAN.md`를 채운다. 요구사항이 모호하면 추측하지 말고 멈춰서 질문 목록을 만든다. 명시되지 않은 위험 시나리오도 찾는다.
2. 먼저 한 명령으로 빌드·실행되고 헬스체크에 응답하는 최소 버전을 만든다.
3. 그다음 핵심 요구사항을 테스트로 고정하고 통과시킨다. 핵심 제약은 여러 번 반복 실행해도 지켜지는지 확인한다.
4. 나머지 기능은 `docs/PROGRESS.md` 순서대로 한 번에 하나씩, 테스트 먼저.
5. 기능이 끝날 때마다 `docs/playbook/checkpoint.md` 절차를 따른다.
6. 추가 기능은 기존 흐름에 통합하고 문서화할 수 있을 때만 넣는다. 많이 만드는 것보다 이유를 설명할 수 있는 것이 중요하다.

## 단계별 도구
설치된 스킬은 단계에 맞을 때 사용한다. 없는 스킬은 건너뛰고 같은 목적을 직접 수행한다.
- 실무자 대화 전: `to-questionnaire` → 대화 후 `docs/playbook/interview.md`
- 도메인 개념: `docs/playbook/research.md` (웹 검색 / fetch) → 용어 정돈 `domain-modeling`
- 목표 정의: `define-goal` → 설계 빈틈 점검 `grill-me` (요구사항이 모호할 때만)
- 계획: `writing-plans` 또는 `/plan` → `docs/PROGRESS.md` 기능 목록
- 구현: `test-driven-development`, 데이터 분석이면 `jupyter-notebook`, 웹 화면 동작 확인은 `playwright`, 막히면 `systematic-debugging`
- 기능 완료: `docs/playbook/checkpoint.md` / 제출 전: `docs/playbook/wrapup.md`
- 대화가 길어지면 `handoff`

## 완료 기준
- 테스트와 헬스체크를 이번 변경 이후 실제로 실행했고, 출력에서 통과를 확인했다.
- 명령 출력 없이 "완료", "동작함"이라고 말하지 않는다.
- 테스트를 수정하거나 삭제해서 통과시키지 않는다.

## 문서 (필요할 때만 읽기)
- `docs/PLAN.md`: 문제·요구사항·위험 시나리오·성공 기준. 범위가 헷갈릴 때.
- `docs/GLOSSARY.md`: 도메인 용어. 비즈니스 로직을 건드리기 전에.
- `docs/DECISIONS.md`: 설계·기술 선택마다 한 항목. 근거 코드는 `파일:라인`으로 적는다.
- `docs/VERIFICATION.md`: 검증 결과와 남은 한계.
- `docs/PROGRESS.md`: 기능 목록과 통과 여부.
- 결과물 README: `docs/README_TEMPLATE.md` 형식으로 작성. 처음 보는 사람이 README만 읽고 빌드·실행·테스트할 수 있어야 한다. 과제 안내 문서는 덮어쓰지 않는다 (필요하면 별도 파일로).
- `docs/playbook/*.md`: 위 "단계별 도구"의 해당 단계에 도달했거나 사용자가 요청할 때 읽고 따른다.

## 제약
- 웹 서버는 `0.0.0.0`에 바인딩하고 실행 포트를 출력한다. 서버를 띄운 터미널은 종료하지 않는다.
- 런타임·DB·주요 라이브러리 버전과 환경 가정은 README에 명시한다.
- 새 의존성은 이유를 말하고 추가한다. 개인 API 키·유료 외부 서비스·하드코딩된 비밀값은 쓰지 않는다.
- `~/.codex/config.toml`과 `probe-managed-mcp` 블록은 수정하지 않는다. MCP 등록은 사용자가 MCP 탭에서 한다.

## 금지 (시험 환경 규칙)
- `git push`·원격 저장소 추가를 하지 않는다. 커밋까지만. 공개 저장소 `git clone`만 허용된다.
- 문제·파일·결과물을 외부로 전송하지 않는다 (업로드, gist, pastebin, 외부 API로 데이터 전송 등). 외부 접근은 공개 자료·패키지를 받아오는 용도만.
- 차단·제한을 다른 경로나 설정 변경으로 우회하지 않는다. 플랫폼 관리 설정·감독·연결 프로세스를 수정·종료하지 않는다.
- 키·토큰·비밀번호를 출력하거나 파일에 쓰지 않는다.
- Computer Use(데스크톱·화면 자동 조작)는 사용하지 않는다. 웹 동작 검증은 Playwright(헤드리스)로 본인 서버(`localhost`)만 대상으로 한다.
- 외부 코드로 결과물을 통째로 대체하지 않는다. 외부 코드는 참고·라이브러리로만 쓰고 출처를 남긴다.
- 메모리를 과도하게 쓰는 작업(대용량 데이터 전체 로드, 무제한 병렬 실행)은 실행 전에 사용자에게 알린다.
- 과제 안내 문서(`README.md` 등)는 덮어쓰거나 삭제하지 않는다.

## 커밋
- 동작하는 작은 단위마다 커밋. 형식: `feat:`, `fix:`, `test:`, `docs:`, `refactor:`
- 메시지에는 무엇보다 왜를 적는다. 테스트 실패 상태로 커밋하지 않는다.

## 토큰 절약
- 큰 파일·데이터는 통째로 읽지 말고 검색하거나 필요한 범위만 읽는다.
- 긴 명령 출력은 요약해서 보고한다. 코드 전체를 다시 출력하지 않는다.

## 사용자와 일하는 방식
- 설계 결정 지점에서는 바로 구현하지 말고 대안 2개 이상과 트레이드오프를 짧게 제시한 뒤 사용자가 고르게 한다.
- 단순한 해법을 고를 때는 왜 이 범위에서 충분한지, 어떤 조건에서 깨지는지 함께 말한다.
- 각 단계를 마치면 무엇을, 왜 바꿨는지 3줄 이내로 설명한다.
- 도메인 용어가 처음 나오면 한 줄 정의를 붙이고 `docs/GLOSSARY.md`에 추가한다.
